# RDNA3 MoE 内核优化实录（o1–o14）

这份文档记录 FlyDSL 里 RDNA3（gfx1100，wave32）MoE 内核从能跑到跑得快的十几轮优化：
每一轮的**症状是什么、当时猜错了什么、怎么把真正的原因逼出来、改了什么、拿到了多少**。

写给想学这套方法的人，所以重点不在结论，在推导。前六轮里有三轮的第一个解释是错的，
这些错误都保留在文档里——排查过程中"排除一个看起来很合理的解释"往往比最后那行改动
更值钱。

**o7 和 o8 整轮都是负的，而且是同一个错误犯了两次。** o7 按前六轮攒下的模型算出消除
padding 值 +3.7%，做出来是 −9.5%；o8 把 dispatch 的几步分开计时，加起来说合并 collective
值 −20%，做出来是 +4%。两次都是**把独立测量的几步加起来，当成装配好之后的样子**。两轮
都没有产生任何生产代码改动，分别写在 [§5.1](#51-消除-padding-浪费--试过了是负的o7) 和
[§5.3](#53-ep把-meta-并进-payload-的-collective--试过了是负的o8)，方法上的那一课在
[§1.6](#16-工作量的占比不是时间的占比)。负结果里捞出来的东西反而不小：o7 量出了 padding
的真实天花板，o8 撞出了 `all_to_all_single` 的两个尺寸效应，其中一个是 10 倍的带宽悬崖。

**o9 把那一课用上了：先量天花板，再决定要不要写机制。** 它拆掉 decode dispatch 里的主机
同步，decode 整层 −11%（EP=4，加图捕获后抖动从约 100 µs 降到 3 µs），而 prefill 上是
+5%——所以它是一条要显式打开的 decode 路径，不是新默认值。这一轮里分步求和的偏差方向
恰好和 o7/o8 相反，[o9](#o9--固定容量的-dispatch把主机踢出-decode) 里解释了为什么。

配套的可运行脚本在 [`repro/`](repro/)，每一版一个。建议边读边跑。实测数据（v1–v3 / o1–o6 /
torch，多个 shape，以及 EP=1/2/4 的扩展曲线）整理在 [`BENCHMARK.md`](BENCHMARK.md)，
那里也说明了哪些数字之间**不可比**。

## 0. 背景：这套内核在做什么

### MoE 的 GEMM 和普通 GEMM 差在哪

一个 MoE 层做三件事：gating 决定每个 token 走哪几个专家（topk 个），然后每个专家
对分给它的 token 做两次矩阵乘（`gate_up` 升维 + `down` 降维），最后把 topk 份结果
加权求和。

关键差别在于**每个专家拿到的行数是运行时才知道的**，而且各不相同。这带来两个后果，
它们几乎解释了本文全部六轮优化：

1. **需要一个 routing 步骤**：把 `[tokens, topk]` 的专家 id 按专家分组、排序、
   补齐到 tile 边界，产出内核能直接用的 `sorted_ids` / `expert_ids`。这一步的开销
   在 decode（token 很少）时可以超过 GEMM 本身——**o1、o2、o4 都在打这个**。
2. **GEMM 是"分组"的且 M 方向很瘦**：一个 1024 token、topk=2、8 专家的层，每个专家
   平均只有 256 行，却要乘一个几万乘几千的权重。算术强度低，且行数补齐到 tile 会
   产生浪费——**o3、o5、o6 都在打这个**。

### 硬件约束

RDNA3 上跑 WMMA，有三个硬上限，后面反复出现：

| 资源 | 上限 | 谁会先撞上 |
|---|---|---|
| 每线程 VGPR | **256** | 累加器多的 tile（o3） |
| 每工作组 LDS | 64 KB（超过 32 KB 就一个 CU 只放得下一个工作组） | `BLOCK_K` 大的 tile（o3） |
| Infinity Cache | 96 MB | 权重超过它的大模型（o6） |

本机实测的天花板（`repro/roofline.py`，你自己跑一遍）：

```
dense bf16 4096^3 (rocBLAS)     66.73 TFLOP/s
dense bf16 8192^3 (rocBLAS)     68.99 TFLOP/s
streaming read 1.50 GB           830.5 GB/s
```

### 版本线和优化线

仓库里有两条并行的线，别混淆：

- **v1–v5 是功能线**：v1 分组 GEMM + A-gather → v2 融合 gate/up → v3 单机多卡专家
  并行（EP）→ v4 跨机分层 EP → v5 主流模型 shape 覆盖（不是新能力，是宽度）。
- **o1–o7 是优化线**，每一版一个可测的 delta。o1/o2/o3/o5/o6 打单卡计算路径，
  o4 打 v3 的 EP dispatch，o7 是负的、没进生产（§5.1）。

代码位置：

```
kernels/moe/rdna3_moe/
  routing.py          torch 参考实现的 routing（也是正确性基准）
  routing_kernel.py   o1/o2 的 routing 核
  grouped_gemm.py     核心：分组 GEMM，A-gather + scatter + silu
  host.py             tile 表、shape override、编译入口
  forward.py          单卡一层的闭环
  ep.py               专家并行的 dispatch / combine
  dispatch_kernel.py  o4 的一次性 plan 核
```

## 1. 贯穿全程的方法

这六条是七轮下来沉淀出的工作方式，比任何单个优化都通用。最后一条（1.6）是 o7 用一整轮
负结果换来的，也是唯一一条讲"前面几条会怎么骗你"的。

### 1.1 先量天花板，再谈优化

"62 TFLOP/s"这个数字本身没有意义，除非你知道这台机器能到多少。o6 之所以能发现还有
空间，就是因为先测了三个数：稠密峰值、显存带宽、以及**同样形状下库函数能做到多少**。

反过来说，如果不先测，很容易把"接近某个数"误当成"接近极限"。o6 开始时的判断就是错的：
62 TF/s 看着已经贴近 rocBLAS 的 68 TF/s，像是没空间了。

### 1.2 数清楚你**真正**做了多少活

这是 o6 的转折点。把 padding 算进去之后，内核的真实 MAC 吞吐是 ~82 TF/s，
**高于** rocBLAS 的 69 TF/s。于是"68 是天花板"这个前提自己塌了。

一个数字和另一个数字矛盾的时候，不要挑一个信——去查为什么矛盾。矛盾本身就是信息。

### 1.3 写一个能证伪的模型

o6 里写下的模型：

```
时间 ≈ max( B 流量 / 带宽 , 含 padding 的算力 / 吞吐 )
```

它预测 `tile_m=128` 是 10.97 ms，实测 10.97 ms。模型能预测，就能拿它去问"如果我把
B 流量降下来会怎样"，而不用先把代码写出来。模型预测不准，说明瓶颈找错了——这同样
是有用的输出。

`repro/roofline.py` 会把这张表打出来，并且故意留了一处模型与实测不符的地方让你看到
证伪长什么样。

### 1.4 只信同一次会话内的对照

同一份配置，在不同时间测出来能差 5–10%（时钟、温度、其他负载）。o5 记录的
11.64 ms，第二天同配置复测是 12.5 ms——而 torch 侧基本没变。

所以：**A/B 必须在同一个进程、同一段时间里跑完**，报改进只报 delta。跨会话的绝对值
只能当参考。`repro/` 里所有脚本都遵守这条。

对应的操作纪律：不要并行跑两个 benchmark（会争同一张卡），也不要在 benchmark 跑着
的时候改它 import 的文件（这个错误在 o6 里犯过一次，那批数据整个作废）。

### 1.5 先试着证伪你自己的解释

o3 最有价值的一步不是找到答案，是先证明了原来的答案不可能对：两个 tile 的 LDS 占用
分别是 54 KB 和 60 KB，都超过 32 KB，所以**占用率完全相同**——那它就解释不了 6.5 倍
的差距。排除掉之后，才有动力去翻 ISA。

### 1.6 工作量的占比不是时间的占比

1.3 那个模型把 `tile_m` 的交叉点预测到了小数点后两位，然后在 o7 上把人带进了坑里。
它按单一吞吐给工作定价，于是"24.4% 的 MAC 花在 padding 行上"读起来就是"24.4% 的时间
可以捡回来"。实测：整层 padding 值约 11%，一个 padding 行的边际成本只有平均行的三分之
一——因为一次 launch 的大部分时间（权重整流）根本不随行数缩放。

**一个模型只在它建模的那些维度上可信。** 这个模型里没有"每次 launch 的固定成本"这一项，
所以任何改变 launch 次数的方案，它都会算错，而且不会有任何迹象提示你它算错了。o7 的
方案正是把一个 stage 拆成两次 launch。

可操作的两条：

- **要拿一块收益，先直接量它值多少，别从占比推。** o7 用一份恰好不需要补齐的 routing
  （每专家正好 256 行）跑同一个内核，一次就把天花板量出来了——比争论方案怎么设计快得多，
  而且这个数对所有方案都成立。
- **能"免费"拿到的收益，先问代价记在哪一项上。** 拆两次 launch 不改一行内核、数值还
  逐位相同，看着零代价；代价在模型没有的那一项里，2.26 ms，比整个预算还大。

**o8 又犯了一次，换了个形式，所以这一条值得单独记住。** 这回连模型都没有，只是把
dispatch 拆成七步各自计时，再把"新方案的那几步"加起来：`41.0 + 875.9 + 48.5` 对
`49.4 + 656.1 + 28.9`，−20%。实测 +4%。漏掉的仍然是加法看不见的东西——两次为了让数据
连续而做的拷贝，以及原方案里 gather 和主机同步是重叠的、新方案里不是。

**几步各自的时间加起来，不等于把它们装配起来的时间。** 步与步之间有重叠、有缓存状态的
传递、有分配器的行为，这些都不在任何一步的计时里。所以：

- **A/B 要放在同一个进程里交错跑，比较装配好的整体**，而不是比较两组分开量的和。
  `repro/o8_merge_meta_ab.py` 是这个形式：两条路径都实现出来，交替各测 7 轮，报中位数
  和区间，**区间重叠就不算数**。o7 之后加的这条纪律，正是 o8 能在两小时内被否掉的原因。
- **看的指标要是你真正在乎的那个。** o8 里 dispatch 那列有过 −20% 的变体，layer 那列
  全在 ±2% 且区间重叠。dispatch 只占 layer 的 9%，赢它不叫赢。

### o1 — 把 routing 搬到 GPU 上

> 复现：`python3 docs/rdna3_moe_optimization/repro/o1_routing_kernel.py`

#### 症状

32 token（decode）时，三个 GEMM 加 reduce 一共约 69 µs，而**主机上用 numpy 建 routing
要 80 µs**。决定"该乘哪些行"比乘它们还贵。

这类问题的特点是：再怎么调 tile 也找不到它，因为它根本不在 GEMM 里。

#### 改法

新写一个单工作组、256 线程的计数排序核（`routing_kernel.py`）。设计上有个漂亮的点：

一个线程负责一个 `(expert, slice)` 对，`e = tid % E`，`s = tid // E`。因为每个 slice
拥有一段**连续的行区间**，按 `(slice, 区间内位置)` 排序就等于按行号排序——于是
**稳定序是免费的，不需要任何 LDS 原子操作**，全程只要两次 barrier。

`tid % E` 而不是 `tid // S` 也是故意的：同一个 slot 上的线程读同一个地址（广播），
而不是散开访问。

#### 排查中修掉的两个坑

1. **CDNA 的技巧在 RDNA 上是错的。** 原计划用"存到一个巨大的越界下标、让 buffer
   descriptor 把这次写丢掉"这个 CDNA 常用手法。读 `kernels/common/buffer_ops.py` 才
   发现 RDNA 上 `OOB_SELECT=2` 意思是**不做边界检查**，这么写会往野地址上写。改成在
   动态 `if` 里做预测执行的存。
2. **`int(aux[0])` 同步的是默认流，不是你启动核的那条流。** 这是个潜在竞争，改成显式
   `st.synchronize()`。

#### 真正的收获：发现了下一个问题

核本身约 10 µs，但 `build_routing_device(exact=True)` 远不止——因为要把 tile 数读回
主机，那是一次完整的往返。今天实测（`repro/o1_routing_kernel.py` 第 3 段）：

```
 tokens  host numpy  kernel+readback  kernel only
     32       79.8u            68.7u        13.8u
    256       93.9u            68.6u        14.1u
   1024      129.9u            73.9u        14.3u
   4096      316.1u            89.5u        25.8u
```

后两列的差就是读一个 int32 的代价。**这直接催生了 o2。**

（你跑出来的绝对值会不一样，同一台机器不同时间也能差 10% 以上——看列**之间**的关系，
不要看单个数字。这正是 §1.4 那条纪律的由来。）

第二个发现来自把启动批量化之后的测量：耗时随专家数增长很快（E=8 → 8.9 µs，
E=32 → 74 µs，E=128 → 195 µs）。原因是每个 `(expert, row)` 对要做一次 global load，
而且**这次 load 的结果喂给下一次迭代的比较**——是一条依赖链，纯延迟，流水不起来。
加了 `UNROLL=4`（先算四个地址，再发四个独立的 load）之后 E=128 从 195 µs 降到 89 µs。

#### 已知边界（有意留下）

这个设计适合 8–64 个专家。专家数上百时会输给主机。正确的修法不是继续加 slice，
而是把 routing id 先搬进 LDS、用原子直方图统计（只有 scatter 需要稳定序，计数不需要）。
这条写在核的 docstring 里，留给后面的版本。

### o2 — 不要把 tile 数读回主机

> 复现：`python3 docs/rdna3_moe_optimization/repro/o2_sync_free_routing.py`

#### 症状

o1 的核 10 µs，却挂着一个约 30 µs 的主机往返，因为 GEMM 的 grid 需要精确的 tile 数。

#### 关键洞察

**grid 不需要精确，只需要一个上界。** 而上界不用看 routing 就能算：

```python
def max_blocks_for(*, tokens, topk, experts, tile_m):
    # 每个专家 ceil(c/t) < c/t + 1；没有行的专家也占一个 tile，这本身就是它的界
    return experts + (tokens * topk + tile_m - 1) // tile_m
```

于是 grid 用上界，多出来的 tile 由内核自己跳过（`bounded_blocks=True`，从显存里读
真实 tile 数比较）。主机全程不用等。

#### 两个让它成立的细节

1. **提前退出的判断放在内核的末尾，不是开头。** 它之前的全部代码只是地址运算和两次
   标量读取，而 o1 的核已经把超出真实 tile 数的部分填上了 sentinel，所以那些读都是
   良定义的。
2. **判断条件是块号，全工作组一致**，所以内部的 barrier 不会失配。

#### 一个重要认知：这不是正确性修复

超出末尾的 tile 本来就是**安全的**：A 的 gather 走带边界检查的 buffer descriptor，
sentinel 行读回 0；scatter 也带边界检查，所以什么都不写。这个 tile 算一堆垃圾进寄存器
然后丢掉。提前退出**只是省掉这些算术**。

今天实测（`repro/o2_sync_free_routing.py`）：

```
tokens=32 tile_m=16   layer with routing prebuilt: 71.0 us
    routing_impl  layer+route  routing adds
            host       222.0u        150.9u   maxdiff 0.0e+00
    device-exact       168.7u         97.6u   maxdiff 0.0e+00
          device        93.4u         22.4u   maxdiff 0.0e+00
```

三种实现输出逐位相同，routing 给层增加的开销从 151 µs 降到 22 µs。

#### 顺带

同时做的还有 buffer 复用（按 shape 缓存工作区）。`torch.empty` 每次 10–15 µs，
routing 每步要三个——和核本身的耗时一个量级。

还有个测试上的坑：改完之后三个 o1 的测试挂了，因为 `build_routing_device` 的默认值
变成了 `exact=False`，而那些测试比较的是精确的缓冲区长度。修法是在那三个调用点显式
传 `exact=True`。

### o3 — tile 表，以及一个错误的诊断

> 复现：`python3 docs/rdna3_moe_optimization/repro/o3_tile_table.py`
> 证据：`repro/o3_isa_dump.py`（见 [repro/README](repro/README.md)）

这是最值得细看的一版。

#### 症状

`gate_up` 在 `tile_m=128` 上只有 7.4 TFLOP/s，而 `tile_m=64` 有 48 TFLOP/s。
**同一个内核，换个 tile 大小差 6.5 倍。**

#### 当时的解释（写在 `host.py` 的注释里，是错的）

"融合的 gate/up 有两条 B 流，占 60 KB LDS，一个 CU 只塞得下一个工作组，所以占用率低。"

#### 怎么证伪的

算一下就知道不可能：

```
64  tile:  54.0 KB -> 2 waves/SIMD
128 tile:  60.0 KB -> 2 waves/SIMD
```

**两者占用率完全相同。** gfx11 一个工作组最多 64 KB LDS、一个 CU 总共 64 KB，超过
32 KB 就都只能放一个工作组。既然占用率一样，它就解释不了 6.5 倍。

#### 真正的原因

数累加器。融合的 gate/up 用一份 A 喂两条 B 流，所以累加器是 `2 * reg_m * reg_n` 份，
每份 8 个 VGPR：

```
2,2,4,2,2  accs= 8 ->  64 VGPRs
4,4,2,2,2  accs=32 -> 256 VGPRs   <- 正好顶满 gfx11 的上限，其他什么都还没算
```

不猜，去 ISA 里看。`repro/o3_isa_dump.py` 今天跑出来的：

```
grouped_gemm_kernel_0/21_final_isa.s      (4,4,2,2,2 = 128x128x32)
  .vgpr_count:     256
  .vgpr_spill_count: 769

grouped_gemm_kernel_0/21_final_isa.s      (4,1,2,2,2 = 128x32x32)
  .vgpr_count:     201
  .vgpr_spill_count: 0
```

**769 次寄存器溢出。** 这就是那 6.5 倍。

查法（`FLYDSL_RUNTIME_ENABLE_CACHE=0` 不能省，否则可能拿到改动前的二进制）：

```bash
FLYDSL_RUNTIME_ENABLE_CACHE=0 FLYDSL_DUMP_IR=1 FLYDSL_DEBUG_DUMP_ASM=1 \
  FLYDSL_DUMP_DIR=/tmp/isa python3 <脚本>
grep -E 'vgpr_count|vgpr_spill_count' /tmp/isa/grouped_gemm_kernel_0/*_isa.s
```

#### 改法：杠杆 A —— N 方向的宽度从 wave 买，不从寄存器买

`reg_n=1` 配 `waves_n=2` 和 `reg_n=2` 配 `waves_n=1` 覆盖同样的 `BLOCK_N`，
但从 wave 买不花累加器：

```
  reg/waves          block  thr  accs  LDS KB  waves        us  TFLOP/s
  4,4,2,2,2     128x128x32  128    32    60.0    2.0    1742.0     7.40
  4,1,2,2,2      128x32x32  128     8    30.0    4.0     241.1    53.44
```

#### 改法：杠杆 B —— `BLOCK_K` 减半，换第二个工作组

流水线是双缓冲的，`BLOCK_K=64` 会让每个 stage 都过 32 KB，一个 CU 只放得下一个工作组
（2 waves/SIMD，上限是 16）。减到 32 就能放两个：

```
  2,2,4,2,2       64x64x64  128     4    36.0    2.0     125.5    51.33
  2,2,2,2,4      64x128x32  256     4    30.0    8.0     115.1    55.98
```

这是单 B 流那两个 stage 收益的主要来源。

#### 副产品：一个 bug 和一次工程判断

扫描时在第一个配置上就崩了：`reg_m=reg_n=1` 且单 B 流时只有一个累加器，K 循环的
loop-carried state 会退化成裸值而不是长度 1 的序列，`state[:n_acc]` 直接抛 `TypeError`。

值得学的是**修的过程**：先写了个 `_carried()` 帮助函数做防御性包装 → 失败点只是移到了
初始化路径 → 加 `print` 打出实际类型 → 看清之后**放弃了归一化方案**，改成在构建期
直接拒绝这种 tile（一个线程一条 WMMA 本来也填不满流水线）。

> 与其为一个角落情况写脆弱的归一化，不如让它构建不出来。

同时 tile 表改成了**偏好列表**：调优的 tile 排第一，后面跟着 `BLOCK_N`/`BLOCK_K`
更窄的退路，这样 `n_out` 很小的 shape 仍然能建起来而不是直接报错。

#### 另外两个被明确放弃的方向

- **给每个候选都 dump ISA**：约 50 个候选，太慢。改成 LDS 解析计算，只给赢家 dump。
- **用 `git stash` 做新旧 tile 表的 A/B**：`grouped_gemm.py` 同时也改了，扫描脚本依赖
  新版本，回退会失真。改成靠同会话内的扫描对照。

### o4 — EP dispatch 的计划核

> 复现（诊断，单卡）：`python3 docs/rdna3_moe_optimization/repro/o4_ep_dispatch.py`
> 复现（对照，双卡）：`torchrun --nproc_per_node=2 --master_port=29870 <同一个脚本>`

#### 背景：EP 的一个关键设计

交换的单位是**一个 routed slot，而不是一个 token**：topk=2 的 token 发两行，哪怕两个
专家在同一张卡上。代价是多一份 activation 带宽（撞同一张卡的概率 1/world）；换来的是
**每一行只带一个专家**，于是专家卡上 `topk=1`，`moe_forward` 一行都不用改。routing
weight 跟着行走、由 gemm2 折进去，这样算术和单卡路径**逐位相同**，测试才能对精确值
而不是容差。

#### 症状

1024 token/rank 时 dispatch 占 873 µs，是总时间的 77%。

#### 排查三步（这一段是本文最完整的排查示范）

**第一步，先量传输的地板。** 写个微基准直接测 `all_to_all_single`：小包约 64 µs 起步，
大包 12–19 GB/s，**每个 collective 不管搬多少都有 30–60 µs 固定开销**。
（`can_device_access_peer` 是 True，所以这 12–19 GB/s 是真的 PCIe P2P，不是主机中转。）

**第二步，一个没奏效的改动。** 想着三个 collective 里有两个只搬几 KB 元数据，就把
expert id 和 weight 打包成一个 `[rows, 2]` 的 int32 张量，三个并成两个。结果
**873 → 857 µs**，几乎没动。

这一步很重要：它排除了"collective 太多"这个假设。

**第三步，不再猜，逐个算子计时。** 这才找到东西。今天在单卡上复现的结果：

```
op                                                   us  note
torch.bincount(dest)                               83.6  counts 2048 elements
torch.sort(stable) + searchsorted                  48.4  same counts, and the permutation too
.tolist() on a few elements                        29.9  a full device-to-host sync
bool(((ids<0)|(ids>=E)).any())                     61.7  a range check is a hidden sync
  same check kept on device (.sum())               34.4  fold it into the one readback instead
x.index_select (the actual data movement)          24.4  343 GB/s -- NOT a trap, leave it alone
```

注意 `bincount` 在 64 个元素上也要 81 µs、2048 个元素上 84 µs——**跟数据量无关**，
说明它内部在同步（大概是为了确定输出大小）。

#### 光靠这张表就落地的三个修改

- `bincount` → `sort(stable)` + `searchsorted` 取桶边界（sort 顺带把置换还给你，
  连后面的一次 gather 都省了）
- 两次 `tolist()` 合成一次 `torch.cat` 读回
- 范围检查从 `.any()` 转 bool（隐藏同步）改成 `.sum()` 留在设备上，折进同一次读回

**dispatch 857 → 600 µs**，一行内核都没写。

#### 然后才是内核

decode 时 dispatch 是 574 µs，而传输地板只有 107 µs——467 µs 全是二十来次 torch 调用
的固定开销，每次只处理 64 个元素。**这和 o1/o2 在 routing 上遇到的是同一个形状的问题。**

于是 `dispatch_kernel.py`：o1 的计数排序，key 从专家换成目标 rank，去掉 tile padding
（alltoall 要求各目标端的行首尾相接，不能有洞）。

三个设计决定：

1. **大块 gather 留给 torch。** `index_select` 搬 8.4 MB 只要 15.6 µs，那是带宽不是开销，
   重写没有收益。核只做计划和元数据——也就是那些"每次只处理 64 个元素"的活。
2. **counts 缓冲按"一次读回"的布局排**：前 W 个是自己数的、中间 W 个是 counts alltoall
   落地的地方、最后一个是越界计数。主机一次 copy 同时拿到 split sizes 和输入校验。
3. **两个输出宽度不同，是被消费者逼出来的。** 实测验证过：`index_select` 吃 int32，
   `index_copy_` 只吃 int64。所以 `send_order` 在核里直接写成两个 dword（行号非负，
   高位恒零），避免一次转换核。

#### 数字（今天双卡实测）

```
 tokens/rank  plan_impl  dispatch us    delta
          32       host        556.0
          32     device        333.6   -40.0%
        1024       host        634.0
        1024     device        449.8   -29.1%
   payload/x/meta bit-identical between the two plans: True
```

测试断言的是**核的置换、counts、payload、expert id、weight 全都和 torch 路径逐位相同**，
而不只是下游答案对得上。

#### 环境限制

EP=4/8 在默认容器里起不来。`/dev/shm` 只有 64 MB，而 RCCL 每个 communicator 固定要
20.25 MB（试过 `NCCL_SHM_DISABLE`、`NCCL_BUFFSIZE`、`NCCL_MAX_NCHANNELS`，都无效），
所以最多 3 个 rank。修法是 `docker run --shm-size=2g`。测试会带着这个提示干净地 skip。

### o5 — 按 shape 定制 tile

> 复现：`python3 docs/rdna3_moe_optimization/repro/o5_shape_override.py`

#### 症状

在一张覆盖多种 shape 的对比表里，`D4096/I14336`（Mixtral 尺寸）是**唯一一个输给
eager torch 的**：0.92×。

#### 判断

o3 的 tile 表是在 `D2048/I768` 上调的。`I=14336` 是它的近二十倍，N 方向的网格和权重
流量完全不是一回事。这是明确的表失配，不是算术问题。

#### 排查

用 `scripts/sweep_rdna3_moe_tiles.py` 分别扫 `gate_up` 和 `down`。

**这里踩了一个坑值得记：**第一次把两个 stage 的扫描作为两个并行的调用发出去了，
它们争同一张 GPU，数据不可用。整组丢弃，改成串行重测。

#### 结果：两层修复，第一层贡献更大

今天复现的 tile_m 阶梯（只用通用表）：

```
 tile_m           gate_up tile              down tile     layer  TFLOP/s  vs torch
     32      32x32x64 (accs 4)     32x128x32 (accs 4)    16.11m    44.79     1.07x
     64      64x32x64 (accs 4)     64x128x32 (accs 4)    13.46m    53.61     1.28x
    128     128x32x32 (accs 8)     128x64x32 (accs 4)    13.17m    54.78     1.31x
```

**光是把 `tile_m` 从 64 改成 128 就已经越过 torch 线了**，还没动任何 tile 形状。
原来那行 benchmark 用 64 只是因为它是 prefill 的默认值。

第二层才是重新调 128 底下的块形状：

```
 _SHAPE_TILES           gate_up tile              down tile     layer  TFLOP/s
          off     128x32x32 (accs 8)     128x64x32 (accs 4)    13.23m    54.55
           on    128x64x32 (accs 16)   128x128x32 (accs 16)    11.09m    65.04
```

#### 实现

新加一个 `_SHAPE_TILES` 字典，按 `(stage, k_dim, n_out, tile_m)` 索引，命中的 tile
**插到通用偏好列表前面**（所以通用 tile 仍是退路）：

```python
_SHAPE_TILES = {
    ("gate_up", 4096, 14336, 128): ((4, 2, 2, 2, 2),),  # 128x64x32
    ("down", 14336, 4096, 128): ((4, 4, 2, 2, 2),),  # 128x128x32
}
```

**刻意和 `_TILES` 分开**：把这些更宽的 tile 提到通用表的第一选择，会让 o3 调好的
`D2048/I768` 回归。

#### 被否决的：`tile_m=256`

这个 shape 平均每个专家正好 256 行，看起来 256 行的 tile 能让每个专家只用一块、
不再重复加载权重。扫过之后否决了：`gate_up` 确实变快，但 `down` 变慢了。

（`roofline.py` 把这个权衡的两边都量化了：256 的 padding 浪费高达 47.5%。）

#### 防回归

加了两个测试，断言**精确的块几何**——既断言 override 生效，也断言基线 shape 没被动。

### o6 — 同样的 tile，换个派发顺序

> 复现：`python3 docs/rdna3_moe_optimization/repro/o6_grid_order.py`
> 方法：`python3 docs/rdna3_moe_optimization/repro/roofline.py`

这一版一行算术都没改。

#### 起点：一个看起来没空间的局面

o5 之后这个 shape 是 62 TF/s，而 rocBLAS 稠密峰值 68 TF/s——看着已经 91%，像是到顶了。

#### 转折：数清楚真正做了多少活

`tile_m=128` 时每个专家平均 256 行，**正好卡在 128 的边界上**，这是最坏情况：
大约一半的专家会多要一个几乎全空的第三块。实测的浪费：

```
 tile_m  avg tiles  padded rows  wasted MACs
     32       67.8         2168         5.9%
     64       35.8         2292        11.9%
    128       19.9         2547        24.4%
    256       11.8         3021        47.5%
```

24.4% 的 MAC 是白做的。把它算进去，内核的**真实硬件吞吐是 ~82 TF/s，高于 rocBLAS 的
69 TF/s**。

矛盾解开了，而且方向是反的：**这套 WMMA 管线比库快，68 从来就不是天花板。**

#### 模型

每个 M tile 都要完整重读一遍它那个专家的 B 切片，所以权重流量正比于 tile 数；
而算力正比于含 padding 的行数。两者反向：

```
 tile_m   B traffic   DRAM ms  compute ms  model ms  measured
     32     23.88 GB     28.75        9.34     28.75         -
     64     12.61 GB     15.19        9.87     15.19     13.45
    128      7.01 GB      8.44       10.97     10.97     10.97
    256      4.16 GB      5.01       13.01     13.01         -
```

模型在 128 上预测 10.97 ms，实测 10.97 ms。

**`tile_m=128` 之所以最优，不是因为它好，是因为它恰好落在两条约束的交叉点上**——
再小被权重重复读打死，再大被 padding 打死。

> **这个模型有一处会误导人，o7 才发现。** 它给每行按同一个吞吐定价，于是"24.4% 的 MAC
> 是 padding"读起来就像"24.4% 的时间是 padding"。实测不是：整层 padding 只值约 11% 的
> 时间，因为一个 padding 行的边际成本只有平均行的三分之一——一次 launch 的大部分时间
> 不随行数缩放。模型仍然值得留（它把 `tile_m` 的交叉点预测到了小数点后两位），但
> **工作量的占比不等于时间的占比**。详见 5.1。

#### 真正的问题：重复读是调度伪影

`grid` 原本是 `(N_tiles, M_tiles)`，**N 在最内层**。于是同一个专家的两个 M tile 之间
隔着整趟 N 扫描（448 个工作组、约 229 MB 数据流过），缓存必然失效。

把 M 放到最内层，同专家的 tile 背靠背派发，B 只需从显存读一次。改动就是交换 grid
两个维度和 `block_id` 的读取。

#### 但不能设成全局默认

一个工作组读一块 A（`BLOCK_M × k_dim`）和一块 B（`BLOCK_N × k_dim`）。**谁在最内层，
谁的操作数就靠缓存复用，另一个就被重读。** 所以答案取决于哪个操作数更大、以及权重
到底装不装得进缓存。四种组合今天实测：

```
--- D4096/I14336   total weights 2.82 GB   (装不进 96 MB) ---
   stage          block    A tile    B slab  N innermost  M innermost    delta
 gate_up      128x64x32      1.0M      0.5M       65.23T       69.84T    +7.1%
    down     128x128x32      3.7M      3.7M       63.10T       60.00T    -4.9%

--- D2048/I768   total weights 0.08 GB   (装得进) ---
 gate_up      128x64x32      0.5M      0.3M       52.38T       52.09T    -0.6%
    down     128x128x32      0.2M      0.2M       52.60T       51.08T    -2.9%
```

三条结论：

- **宽 shape 的 `gate_up` 是唯一想要 M 最内层的**：权重不命中缓存，且它的 A tile 是
  小的那个操作数。
- **`down` 永远不想要**：它的 `k_dim` 是中间维，A tile 有 3.7 MB（`gate_up` 只有 1 MB），
  而 N 只有 4096（扫描很短），N 最内层本来就给了它很好的复用。
- **基线 shape 也不想要**：整个权重集装得进缓存，B 重读本来就是命中，省不出东西。

所以做成按 `(stage, k_dim, n_out)` 索引的 `_SHAPE_M_MAJOR` 表：

```python
_SHAPE_M_MAJOR = {
    ("gate_up", 4096, 14336),
    ("linear", 4096, 14336),
}
```

#### 数字

同会话交叉对照（消除机器漂移）：

| | override 关 | override 开 |
|---|---|---|
| gate_up | 55.9–57.6 TF/s | 64.5–64.7 TF/s |
| layer+route | 12.41–12.59 ms | 11.67–11.74 ms |
| vs torch | 1.21–1.22× | 1.29–1.30× |

所有配置的数值 diff 都是 0——调度顺序不影响结果。

### o9 — 固定容量的 dispatch，把主机踢出 decode

#### 症状

EP=1 那一列：**payload 是 0.00 MB，交换段仍然要 409 µs。** 一个字节都没出卡，
时间照付。这是 §3.1 那个形状第四次出现，而这次它是 EP=8 撞墙前唯一还能推的东西。

拆开 EP=4 decode 的 dispatch（353 µs）：计划核 28、counts 交换 57、gather 8、
**回读 22**、payload 交换 94、meta 交换 50，加起来 259 µs——还剩约 90 µs 找不到对应的
核，那是主机胶水。而那个 22 µs 的回读是 `plan.counts.tolist()`，`all_to_all_single`
要 split sizes，split sizes 在设备上，所以必须同步一次。

#### 先量天花板

o7 和 o8 都是先做后量，两次都翻车（[§1.6](#16-工作量的占比不是时间的占比)）。这次反过来。

要去掉 counts 交换和回读，正确的做法需要容量、填充行、能跳过填充的 combine——一堆机制。
但**基准测试里路由是不变的**，所以可以先把 counts 算出来一次，然后跑一个把它当常量传进去的
dispatch。少掉的正好是这两步，而且数值完全正确。这就是天花板，不用写一行机制代码。

（[`repro/o9_decode_overhead.py`](repro/o9_decode_overhead.py)，EP=4 decode，同会话交错）

| | dispatch | 整层 |
|---|---|---|
| 现状 | 336.1 [325.6, 376.7] | 1595.8 [1568.5, 1670.0] |
| 固定 split | 227.5 [222.4, 282.2] | **1381.0** [1376.7, 1414.4] |
| 再加图捕获 | （在图里） | **1351.2** [1350.8, 1352.8] |

**注意方向：dispatch 只少了 109 µs，整层少了 215 µs。** 层得到的比 dispatch 失去的多，
因为那个同步不只花掉自己那 22 µs——它堵住了整条队列，让 dispatch 的活没法和层的 launch
重叠。o7/o8 是分步求和**高估**，这次是**低估**，同一个错误的另一面。

#### 改动

落位那一行。原来每个目的地从上一个结束的地方开始，所以块长由路由决定，所以主机必须先
知道它：

```python
first = c0
for rr in range_constexpr(W):
    t = _ld(tot_mr, fx.Int32(rr))
    first = (fx.Int32(rr) < d).select(first + t, first)
```

给定容量之后，目的地 `d` 的槽位就是它的，填不满也是它的：

```python
first = d * fx.Int32(CAP)
```

块长全相等，`all_to_all_single` 自己就能切，counts 交换和回读一起消失。

填充槽位怎么不花钱，是这件事能成的关键。答案在 routing 核里已经写好了——它的直方图和
scatter 都是 `eids[u] == e`，`e` 取遍 `[0, experts)`：

```python
hit = inb[u] & (eids[u] == e)
```

所以**本地专家 id 给 -1 的行既不计数也不散射**，它不进任何 tile，不进任何 GEMM。填充只在
线上花带宽，过了线就一分钱不花。这一点很重要：decode 时 `tile_m=64` 的一个 tile 是
22.5 GFLOP、约 450 µs，要是填充行真的过 GEMM，这条路当场就死了。

combine 那边多一行暂存槽吸收填充：计划把每个填充槽的 `send_order` 指向它，谁也不读。

#### 数字

（[`repro/o9_capacity_ab.py`](repro/o9_capacity_ab.py)，`D4096/I14336`，8 专家，同会话交错）

| 容量 | EP=2 decode | EP=4 decode | EP=8 decode | EP=4 prefill |
|---|---:|---:|---:|---:|
| packed（现状） | 2550.1 | 1616.3 | 1462.9 | 14824.6 |
| 1× 均衡份额 | 溢出 | 溢出 | 溢出 | 溢出 |
| 2× 均衡份额 | **2409.2 (−5.5%)** | **1440.9 (−10.9%)** | **1305.3 (−10.8%)** | 15527.3 (+4.7%) |
| `safe_capacity`（= 全部槽位） | 同上 | 1729.4 (+7.0%) | 1650.0 (+12.8%) | 17230.8 (+16.2%) |
| 2× 均衡 + 图捕获 | **2398.1 (−6.0%)** | **1396.3 (−11.6%)** | — | — |

三件事：

1. **容量因子是有窗口的，不是越安全越好。** 我一开始的默认值是 `safe_capacity`——
   `tokens*topk`，一个 rank 最多也就这么多行发给一个目的地，所以任何路由都溢不出来。
   量出来 EP=4 decode 是 **+7.0%**、EP=8 是 **+12.8%**：它的填充量不随卡数变，而均衡
   份额按卡数缩，所以卡越多它越亏。因子 2 才是甜点，拿到 EP=4 天花板 13.5 个点里的
   10.9 个，填充只吃掉 1.4 个，到 EP=8 仍然是 −10.8%。
2. **prefill 上必然是负的**，这在 5.4 里是推出来的，现在是量出来的：+4.7% / +16.2%。
   prefill 的交换是带宽绑定的，翻倍载荷比省掉的固定开销贵得多。所以**默认必须留在 packed**，
   这是一条 decode 专用路径。
3. **抖动塌掉了。** packed 的区间是 [1568, 1670]，约 100 µs；固定容量是 [1436, 1445]；
   图捕获是 [1395, 1398]，约 3 µs。对服务端的尾延迟，这一条可能比那 10% 更值钱。

#### 溢出：静默错误换成响亮错误

因子 2 是可以被路由挤爆的（prefill 上实测每个 rank 丢 20–44 行），而丢行是静默的数值错误，
最坏的那种失败。检查它却要读设备上的计数——又是一次同步，正是我们刚拆掉的东西。

出路是**延迟检查**：计数异步拷进锁页内存，跟在计划后面按流排序，下一次调用时读——那时
某个更早步骤的值已经落地了。没有人等，图捕获把这个拷贝当普通流操作录进去，而溢出的路由
最多晚一两步就会抛出来。

这不是栅栏：出事那一步已经带着缺失的行发出去了。要绝对不能发生的调用方跑 `safe_capacity`，
路由没有办法溢出它，代价是那些字节。**这是个取舍，不是个解决方案**，文档里就得这么写。

#### 一个 DSL 上的坑，和一个脚本上的死锁

两个都值得记，因为都不是算法问题：

- kernel 体里的 `if` 会被重写成设备侧条件块，所以在分支里赋的值出不来（`NameError`）。
  主机常量分支要用 `if const_expr(...)`，`grouped_gemm.py:337` 就是这个写法。
- A/B 脚本里"这个容量溢不溢出"原本是各 rank 各自算的。**一个 rank 溢出而另一个没有，
  两边就得到不同的 variant 列表，发出不同的 collective 序列，然后整个 run 挂死**——不是
  报错，是挂死。判决必须 `all_reduce(MAX)` 成全组一致。多卡脚本里任何影响控制流的
  设备侧数值都有这个问题。

### o11 — 空专家不再占 tile（稀疏 decode 的全部）

复现：`scripts/bench_qwen38_moe_decode.py --tokens 1 --check`。

Qwen3.8-Flash-Next 在 TP=8 下是 `H=2560 / I=80 / E=513 / topk=11`。这个 shape 把 o1–o9
从来没遇到过的一件事放大了：**专家数远大于一步里的行数**。

routing 原本给每个专家至少一个 tile，理由写在当时的 docstring 里——全是 sentinel 的 tile
gather 出零、什么都不存，只花一个工作组。这句话是对的，但漏了一件事：**那个工作组在
gather 出零之前，先把该专家整块权重从 DRAM 读了一遍**。

一个 token、11 个槽位，真实工作是 11 个专家：

| | tile 数 | 权重读取 | routing | gemm1 | gemm2 | reduce | 整层 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 每专家一 tile | 513 | 601 MiB | 109 µs | 585 µs | 269 µs | 13 µs | **1030 µs** |
| 只给有行的专家 | 11 | 12.9 MiB | 109 µs | 25 µs | 13 µs | 13 µs | 160 µs |

两个 GEMM 一步 854 → 38 µs。改动只有两处：`routing_kernel._tiles` 去掉 `max(1, ...)`，
以及 `max_blocks_for` 的上界从 `E + rows/t` 收紧成 `min(E, rows) + rows/t`——后者同样重要，
因为它同时是缓冲区大小和 grid 的 Y 范围，M=1 时从 514 降到 11。

代价是 `expert_ids` 的长度不再是常数 `E`。原来靠这一点跨步复用一块分配，现在改成按
`max_blocks_for` 的上界分配，行为不变。

### o12 — routing 不再遍历 (专家, 行) 的每一对

复现：`scripts/bench_qwen38_moe_decode.py --tokens 1,16,760`。

o11 之后 routing 成了 decode 层里最贵的一段，而且它随 token 数爆炸：M=760 时 1649 µs，
比它喂的两个 GEMM 加起来还多。

原因是 o1 的线程布局：一个线程是一个 `(专家, 切片)` 对，扫自己那片行找自己的专家。这让
排序天然稳定（切片连续、按序前缀，出来就是主机 argsort 的行序），代价是**每个 (专家, 行)
对都要被某个线程看一遍**，即每线程 `E * rows / 256` 次全局读。E=513、rows=8360 就是
16.7 M 次配对检查。`_chunking` 只是让 E>256 能编译，斜率一点没动。

现在每行只读两遍，一遍直方图一遍 scatter，两遍都是一条 LDS 原子加：

```
histogram   ds_add_rtn_u32 到每专家一个计数器
scan        对每专家 tile 数做块内 Hillis-Steele（8 步），得到每专家的起始槽位，
            就地写回计数器 —— 同一个数组接着当 scatter 的游标
scatter     ds_add_rtn_u32 返回的旧值就是这一行的槽位
```

| tokens | 配对遍历 | 原子直方图 |
|---:|---:|---:|
| 1 | 16 µs | 6 µs |
| 16 | 42 µs | 6 µs |
| 760 | 1649 µs | 13 µs |

**丢掉的是稳定序**：谁抢到原子谁占槽位。层的输出不受影响也依然确定——每行是独立的点积，
packed id 自带它要 scatter 回去的 `(token, slot)`——变的只是 `sorted_ids` 与主机构建器
仅在每个专家内部相差一个置换。`test_device_routing_matches_the_host_builder` 因此改成
先把每个专家的槽位区间排序再比（sentinel 比任何真实 id 都大，排序自然把 padding 留在末尾）。

顺带：`_chunking` 和那个 256 宽的展开扫描一起没了，E=513 的 routing 核编译时间从 ~700 s
降到 ~15 s。

### o11 + o12 的端到端结果

`vllm bench serve`，Qwen3.8-Flash-Next、TP=8、CUDA Graph、760 输入 / 16 输出：

| | TPOT |
|---|---:|
| 原生 vLLM（triton fused_moe） | 19.38 ms |
| FlyDSL 改前 | 66.94 ms |
| FlyDSL 改后 | **19.86 ms** |

从慢 3.46× 变成持平。改后 trace 里 MoE 占 decode 步约 11%（`grouped_gemm` 36.5 µs × 2 +
`routing` 7.0 µs + `moe_reduction` 3.3 µs，每层每步）；剩下的大头是 attention 26% 和
TP all-reduce 23%，都在这个内核的范围之外。

**这一轮里"原生 vLLM"那一列走的是默认 MoE 配置**，不是它的上限。补上调优之后结论会变，
见下一节。

### o13 — 给原生 vLLM 补调优，然后重新问"谁更快"

复现：`scripts/tune_vllm_moe.py`，以及 `bench_qwen38_moe_decode.py --vllm`。
详细数据在 [`BENCHMARK.md` §10](BENCHMARK.md#10-o11--o12专家数远大于行数时-qwen38-flash-next-tp8)。

o11/o12 那张表里的对照有两个毛病，都得先修掉才能谈"谁最快"。

**其一：两边的数不是一个口径。** 291 µs 和 1852 µs 来自别处的测量，迭代次数、是否图重放、
gating 算不算在内都不一样。所以 `bench_qwen38_moe_decode.py` 加了 `--vllm`：在同一个进程、
同一份输入、同一个 `_bench_graph` 上跑 vLLM 的 `fused_experts`，两列才可减。

**其二：`E=513 / N=80` 没有调优表，走的是默认启发式。** 补一张出来，同口径下（图重放，
三轮取中位数）：

| | M=1 | M=16 | M=760 |
|---|---:|---:|---:|
| vLLM 默认配置 | 61.1 µs | 311.5 µs | 1920.9 µs |
| vLLM 调优后 | **52.7 µs** | **295.0 µs** | **1097.1 µs** |
| FlyDSL（o12 之后） | 57.1 µs | 303.2 µs | 1133.6 µs |

> M=1 那一列后来发现整体偏高约 15 µs：当时 `_bench_graph` 一张图只捕一次调用，
> `graph.replay()` 自己的主机开销就进了读数。三个臂偏得一样多，所以列内可比，但绝对值别
> 拿去和 o14 的表对照——那张表是修完之后测的。

**调优把原生从落后变成小幅领先，M=760 上值 43%。** 内核这一层的结论因此反过来：
tuned triton 在三个尺寸上都快 3–8%。这也说明 o11 那一课不只是 FlyDSL 的——默认启发式在
M=760 挑了 `128x128x64`，而调优选出来的是 `16x64x128`，专家数远大于行数时**高的 M tile
就是错的**，triton 那边同样如此。

端到端则看不出差别（今天重测，四个 seed）：

| | TPOT | TTFT |
|---|---:|---:|
| 原生 vLLM，默认 | 19.83 ms | 343.9 ms |
| 原生 vLLM，调优后 | 19.84 ms | **328.6 ms** |
| FlyDSL | 19.88 / 20.00 ms | 332.3 ms |

TPOT 四个臂全在 19.7–20.0 之间，分不开——MoE 只占 decode 步 11%，内核上那 5 µs 一层摊进去
就沉了。调优吃到的是 **TTFT −4.4%**，因为 prefill 正是内核差距 43% 的那个尺寸。

**一个必须记下来的坑：原生路径跑的根本不是 `E=513`。** 第一次调完表，服务起来日志说
`Config file not found at .../E=512,N=80,...`——`VLLM_ROCM_USE_RDNA3_MOE=0` 时共享专家没有

FlyDSL adapter 自己的融合视角。查表的键来自 `w2.shape`，**不是模型 config 里的
`num_experts`**，一字之差就是十五个小时白跑。任何跨实现的对照都要先让服务自己把它查的
文件名打出来。

调优本身也有两个可操作的教训，见 [§5.7](#57-给-triton-fused_moe-调优本身的两个坑)。

### o14 — `inter_dim=80` 把 tile 选择挤成一维，那一维没扫完

复现：`scripts/bench_qwen38_moe_decode.py --vllm`。
详细数据在 [`BENCHMARK.md` §12](BENCHMARK.md#12-o14inter_dim80-那一维)。

o13 说 tuned triton 在三个尺寸上都快 3–8%，那就去看 3–8% 在哪。M=1 分段是
routing 8.2 / gemm1 20.5 / gemm2 9.3 / reduce 4.8 µs——**gemm1 一个占掉一半**。

看它拿到的 block 就知道为什么：`16x64`，grid `(5, 11)`，**每个 workgroup 一个 wave32**。
55 个 workgroup × 32 线程铺在 96 个 SIMD 上。原因是 `_candidates` 一路落空：
`n_out=80`，而 `BLOCK_N = 16 * reg_n * waves_n` 必须整除 `n_out`，`80 % 32 != 0`，所以
**BLOCK_N 只能是 16**；BLOCK_N 是 16 就意味着 `reg_n = waves_n = 1`，`tile_m=16` 又把
`waves_m` 钉成 1。三张表全部不命中，最后落到枚举兜底 `_narrowings`。

于是 N 和 M 两个方向都没有旋钮了，**只剩 BLOCK_K**。而 `_narrowings` 只枚举到 `reg_k=4`
（BLOCK_K=64）——2560 明明也能被 128 整除。把这一档补上（gemm1 单独计时）：

| BLOCK_K | M=1 | M=16 | M=760 |
|---|---:|---:|---:|
| 16 | 27.5 µs | 203.0 µs | 1561.7 µs |
| 32 | 23.1 µs | 189.7 µs | 817.4 µs |
| 64（兜底选的） | 19.0 µs | 149.1 µs | 626.4 µs |
| **128** | **15.3 µs** | **132.5 µs** | **574.3 µs** |
| 256 | 17.2 µs | — | 593.7 µs |

**单深一档 BLOCK_K，gemm1 −20% / −11% / −8%**，128 之后掉头。这一条不是"更多并行"——
并行度一点没变，还是一个 wave。省下来的是 barrier：k-loop 每一步一个 `s_barrier`，而一个
只有单 wave 的 workgroup 没有任何别的东西可以拿来盖住它，所以步数减半几乎是等额的收益。
**当占用率已经被 shape 锁死时，能动的就只有每步的固定开销。**

`down` 那一侧（`k_dim=80` 同理把 BLOCK_K 钉在 16，但 BLOCK_N 自由）扫下来基本是平的——
M=760 上 32/64/128 全在 409 µs 上下，因为它已经贴在带宽墙上了；只有 M=1 上 `16x64` 比
`16x128` 值 0.9 µs。两条都写进了 `_SHAPE_TILES`。

同一进程、同一天、同一 `_bench_graph`（图重放，µs）：

| | M=1 | M=16 | M=760 |
|---|---:|---:|---:|
| FlyDSL o13 | 42.0 | 292.7 | 1123.0 |
| vLLM 调优后 | 37.7 | 284.0 | 1085.5 |
| **FlyDSL o14** | **34.4** | **261.7** | **1073.1** |
| 对 tuned triton | **−8.8%** | **−7.9%** | **−1.2%** |

**三个尺寸全部反超。** 两个旁证说明这是对的而不是碰巧：其一，vLLM 自己的调优器在 M=1 和
M=16 上独立选中了 `BLOCK M16xN16xK128`——和我扫出来的完全同一个形状，两条独立搜索收敛到
一处；其二，M=760 上领先只有 1.2%，而那里 FlyDSL 读了 843.8 MiB / 1073 µs ≈ 784 GB/s，是
W7900D 864 GB/s 的 **91%**，两边都已经在带宽墙上，本来就不该有大差距。

要继续拉开 M=760，得减流量而不是调 tile：513 个专家的权重合计 601 MiB，远超 96 MB
Infinity Cache，720 个 tile 里同专家的重复读基本都是 miss。

## 3. 横向：反复出现的三类问题

回头看，六轮其实只有三种毛病。

### 3.1 贵的不是活，是叫这些活的次数（o1 / o2 / o4）

三轮里都是同一个形状：单看每个操作都不慢，但 decode 时数据量小到**每次调用的固定
开销压倒一切**。

识别信号：**耗时和数据量脱钩。** `bincount` 在 64 个元素和 2048 个元素上都是 ~82 µs，
这就是它在同步的铁证。

修法也一样：把 N 次启动压成一次，把 N 次同步压成一次，并且把不依赖读回的活全部排到
同步之前。

### 3.2 你以为撞的上限，不是真正撞的那个（o3）

以为是 LDS/占用率，其实是寄存器。**分辨方法：先算清楚你以为的那个上限，看它能不能
解释观测到的差距。** 算不出来，就说明猜错了。

推论：找到能直接测量的证据（这里是 ISA 里的 `vgpr_spill_count`），别停在推理上。

### 3.3 参数表是跟着 shape 走的，不是全局的（o5 / o6 / o14）

同一份 tile 表在 `D2048/I768` 上是最优，在 `D4096/I14336` 上输给 torch。同一个派发
顺序在宽 shape 上 +7%，在基线 shape 上 -0.6%。

**判据要写成物理量，不是 shape 尺寸本身。** o6 的判据是"权重集装不装得进缓存"，
这样换一台缓存大小不同的卡，或者换一个新 shape，你知道该怎么重新判断。这也是为什么
`host.py` 里那两段注释写的是推导而不是结论。

o14 是这条的另一面：**兜底枚举也是一张跟着 shape 走的表，而它的边界是随手定的。**
`inter_dim=80` 让整个 N 和 M 方向的搜索空间坍缩成一个点，三张 override 表全不命中，
唯一还能动的 BLOCK_K 却在 `_narrowings` 里只枚举到 64——一个当初照着"宽 shape 不需要
更深的 K"定下的上界，在这个 shape 上正好砍掉了最优解。所以**新 shape 上先确认自己落在
哪张表上**：落到兜底里，就要连兜底的枚举范围一起重新问一遍，而不是只在命中的表里调。

## 4. torch 陷阱清单

这些和 MoE 无关，任何写 GPU 侧 Python 的人都会撞上。`repro/o4_ep_dispatch.py` 单卡跑
就能把它们全部复现出来。

| 陷阱 | 代价 | 修法 |
|---|---|---|
| `torch.bincount` | ~82 µs，**与元素数无关**（内部同步以确定输出大小） | `sort(stable)` + `searchsorted`，还顺带拿到置换 |
| `.tolist()` / `int(t[0])` | ~30 µs，阻塞在此前所有 GPU 工作上 | 合并成一次读回（`torch.cat`） |
| `((x<0)|(x>=n)).any()` 转 bool | ~60 µs，**范围检查是隐藏的同步** | 改 `.sum()` 留在设备上，折进同一次读回 |
| `torch.empty()` | 10–15 µs/次 | 按 shape 缓存工作区 |
| `int(t[0])` 同步的流 | 同步的是**默认流**，不是你启动核的那条 | 显式 `stream.synchronize()` |
| `index_select` vs `index_copy_` | 前者吃 int32，后者只吃 int64 | 让核直接产出消费者要的宽度 |
| `index_select` 本身 | **不是陷阱**：8.4 MB / 15.6 µs = 带宽级 | 别重写它 |

最后一条同样重要：**知道什么不该优化**，和知道什么该优化一样值钱。

还有一条不在表里但更关键的：**顺序比调用次数更重要**。把所有不依赖读回的工作排到
同步之前，那一次等待就能同时覆盖交换和 gather。

## 5. 没做的优化

都量化过，按"收益/代价"排序。

### 5.1 消除 padding 浪费 —— 试过了，是负的（o7）

这一条原来写的是"剩下最大的一块，估值约 1.5 ms"。o7 去做了，结论相反，所以留在这里
的是过程而不是待办。复现：`repro/o7_padding_predict.py` 和 `repro/o7_padding_measure.py`。

**方案**：按专家发满整的 128 行主 tile，余数进一个短尾 tile：

```
n_main = c // 128                主 tile，天然满，完全不用补
n_tail = ceil((c % 128) / 64)    尾 tile，补齐到 64
```

302 行的专家变成 2 主 + 1 尾 = 320 行，补到 128 要 384 行。整条 routing 的浪费从 24%
降到 12%，尾 tile 用 32 行则降到 6%——**这部分完全符合预期**。

**而且比预想的好做**。两件事让它几乎不用改内核：`BLOCK_M` 是编译期常量，所以"混合高度"
就是把现有内核在两组互补的行上各发一次；stage1 的输出是按 packed token id 寻址的，不是
按 routing 行序，所以 stage2 可以用一份完全不同的行序去读它——两个 stage 并不真的必须
共用一份 routing。原型和 torch 数值一致，甚至和 uniform 逐位相同。

**结果**：整层 10.80 ms → 11.92 ms，**慢 9.5%**。预测是 +3.7%。

**错在哪**：预测先量了每个 tile 高度的"每行成本"，再按这个成本给方案定价。把 stage1
的两次 launch 单独计时就看见问题了：

| launch | block | tiles | rows | ms | MAC TF/s |
|---|---|---:|---:|---:|---:|
| uniform | 128x64 | 20 | 2560 | 7.01 | 85.8 |
| main | 128x64 | 12 | 1536 | 5.13 | 70.3 |
| tail | 64x128 | 12 | 768 | 3.56 | 50.7 |

**同一个 128 高度，只因为携带的行数从 2560 掉到 1536，速率就从 85.8 掉到 70.3。** 所以
速率从来不是高度的属性。每次 launch 都必须把 8 个专家的权重整流一遍——1.88 GB，按这张卡
830 GB/s 算是 2.26 ms——这笔钱是**按 launch 付的**，摊在这次 launch 恰好带了多少行上。
把一个 stage 拆成两次，就是白买一遍权重。

**顺手把整件事的天花板量了**，这比证伪单个方案有用：喂给内核一份恰好不需要补齐的
routing（每专家正好 256 行 = 两个满的 128 tile），和真实 routing 比：

| stage | routing | tiles | rows | 浪费 | ms |
|---|---|---:|---:|---:|---:|
| gate_up | 真实 | 20 | 2560 | 25.0% | 6.99 |
| gate_up | 均衡 | 16 | 2048 | 0% | 6.38 |
| down | 真实 | 20 | 2560 | 25.0% | 3.87 |
| down | 均衡 | 16 | 2048 | 0% | 3.32 |

**整层 padding 一共值 1.16 ms / 10.80 ms ≈ 11%**，而且这是"免费拿掉"的上限。一个
padding 行的边际成本约 1.1 µs，平均行是 2.7 µs——**只有三分之一**，因为一次 launch
的大部分时间根本不随行数缩放。

于是：`roofline.py` 说"24% 的 MAC 是白做的"没错，但那个模型给每行按同一个吞吐定价，
所以读起来像"24% 的时间"。**工作量的占比不是时间的占比**，两者差了一倍多，而 o7 的方案
就死在这道缝里。任何要拿这 11% 的做法都必须留在**一次** launch 内，在调好的内层循环里
跳过填充行——那是整个内核里对调度最敏感的地方，为了最多十分之一。所以这条不做。

**副产品，也是同一个陷阱**：`o7_padding_predict.py` 第 1 节的配置扫描发现，这个 shape
上 64 高度的生产配置 `64x32` 比 `64x128` 慢 24%（60 vs 75 TF/s）。听着像张免费的表补丁，
放进整层一测：`64x128` 只在 512/1024 token 上赢，而那个区间层本来就会选 128 高度、并且
128 比两者都快；在真正会用到 64 高度的 128/256 token 上，通用的窄 N 配置反而快 7–20%。
**单阶段、单 token 数的测量不能外推到整层**——这和主方案栽的是同一跤，所以生产表没动。

### 5.2 o1 的大专家数扩展性 —— 做了，见 o12

原来的条目是"设计适合 8–64 个专家，上百时输给主机；做法是原子直方图；估值 E=128 时
~89 µs 降到 2 µs 量级（未验证）"。Qwen4Exp 的 513 个专家把它从"以后再说"变成了必须做的，
实测比当年的估算还好一档（M=760 时 1649 → 13 µs）。当时列的代价——"跨 tile 的前缀和会
变复杂"——没有兑现：块内 Hillis-Steele 加一个跨 chunk 的进位就够了，反而比它替换掉的
展开扫描短。**丢掉稳定序是真实代价**，见 o12。

### 5.3 EP：把 meta 并进 payload 的 collective —— 试过了，是负的（o8）

复现：`repro/o8_ep_breakdown.py`、`repro/o8_alltoall_size.py`、`repro/o8_merge_meta_ab.py`。
详细数据在 [`BENCHMARK.md` §9](BENCHMARK.md#9-o8合并那个-collective-值多少不值)。

**当时的理由。** dispatch 送三个 collective（counts / payload / meta），每个不管搬多少
都要 45–60 µs 的固定开销，所以搬 8 字节的那个几乎和搬 8 KB 的一样贵。把 meta 附在
payload 的行后面就能省掉一个。逐段计时支持这个判断：EP=4 prefill 下，
`gather 41.0 + payload 875.9 + meta 48.5 = 965.4 µs` 对
`填充 49.4 + 合并 a2a 656.1 + 解包 28.9 = 734.4 µs`，**−20%**。

**实测是 +4%。** 同进程交错、7 轮中位数，dispatch 从 1021.9 µs 变成 1065.5 µs。

**差在哪。** 两笔没进模型的成本：发送端要把 activation 拼进宽缓冲，接收端要拷回连续
内存——GEMM 的 `ld_a` 写死等于 `k_dim`（`grouped_gemm.py:202`），带着 metadata 的行喂
不进去。这两次拷贝加起来差不多就是省下的那个 collective。**和 o7 是同一种错误：把独立
测的几步加起来，当成装配好之后的样子**（§1.6）。

**排查中真正的收获，两个都和 MoE 无关，是 `all_to_all_single` 本身的性质。**

第一个是地雷。**每目的地的块不是 16 字节整数倍，带宽掉到 1/10**（21 GB/s → 2 GB/s）。
块是 `行数 × 行宽`，行数由路由决定，所以只有**行宽本身**是 16 的倍数才安全。给 D4096
的 bf16 行加两个 int32 正好是 8200 字节：偶数行对齐，奇数行不对齐——于是它只在一部分
路由下爆炸。第一版实现比它要替换的东西慢 10 倍，全部是这个原因，而且如果只在一个
routing 上测过，很可能就漏过去了。

第二个是台阶。**每目的地 4 MiB 之下 16.7 GB/s，之上 20.7 GB/s。** 而 dispatch 的
payload 是 `tokens × topk / world_size` 行 × `model_dim × 2` 字节，在真实模型里全是 2 的
幂——**它按构造就落在整数尺寸上**。EP=4、每 rank 1024 token、D4096 的块恰好是 4 MiB，
正好在慢的那一侧。把行填 256 字节跨过去，dispatch 快 8.4%，这是整张表里唯一区间不重叠
的收益。`NCCL_PROTO` 和 `NCCL_BUFFSIZE` 都调不动它。

**为什么还是没落地。** 那 8.4% 不来自合并，来自跨台阶；而块在台阶哪一侧跟着
`world_size` 走——同样的填充在 EP=2（块已经 8.4 MB，本来就在快档）是 **+6.6%**。要吃这
块收益就得按块尺寸做条件判断，为 layer 层面约 2% 的量，还要在每个新 shape 上重新验证。
这正是 §3.3 说的那种"参数表跟着 shape 走"的东西，只是收益不够买它的维护成本。

### 5.4 EP：固定每对 rank 的行数 —— 做了，见 o9

做完了，在 [o9](#o9--固定容量的-dispatch把主机踢出-decode)。当时这里估的是"decode 的
dispatch 省约 70 µs"，实测整层省 215 µs——因为那个同步堵的是整条队列，不只是它自己那
22 µs。当时推的"prefill 上必然是负的"也对，量出来 +4.7%，所以它是显式打开的 decode
路径。唯一估错的是容量该取多大：我以为该取溢不出来的那个上界，那个上界实测 +7.0%。

### 5.5 decode 图捕获 —— 做了，见 o9

跟着 5.4 一起做完了。o2 的提前退出机制（grid 用固定上界）确实已经是需要的那一半，
补上固定容量之后 `torch.cuda.CUDAGraph` 直接能录，RCCL 的 collective 也能录。
在固定容量之上只再值 1.5 个点，但抖动从约 100 µs 塌到 3 µs。

### 5.6 wave32 P2P 替换 RCCL 的节点内路径

现有的 `flydsl_dispatch_combine_intranode_*` 是 wave64 + mori 的，**不能 fork 到 gfx11**，
要重写。Navi 节点内是 PCIe P2P 不是 XGMI，收益上限受限于那 12–19 GB/s。

### 5.7 给 triton fused_moe 调优本身的两个坑

**其一：并行度要按搜索空间切，不是按 batch size 切。** `benchmarks/kernels/benchmark_moe.py`
一张卡认领一个 batch size，而 batch size 不可分——`E=513` 时 ROCm 剪枝后 `M=1024` 还剩
25760 个配置，每个约 0.9 s，那就是抽到它的那张卡干九小时、其余七张看着。`tune_vllm_moe.py`
改成八张卡各取搜索空间的一个跨步、报各自最优、驱动取 min，同一个 batch size 就能吃满八卡
（`M=1` 从 628 s 降到 25 s）。顺带它也不需要 Ray——服务镜像里没有，而且这台机器连不上 PyPI。

**其二：尾部那 4% 的大 tile 能吃掉比其余 96% 还多的时间。** `M=512` 那档跑到 3000/3112
之后，最后 112 个配置花了超过三个半小时，全在 LLVM 里编 `256x256` 这类 tile。而这个 shape
上它们一个都赢不了：每个专家摊到的行数太少，从 `M=1` 到 `M=512` 选出来的 M tile 全是 16
或 32。加一个 `--max-block 128` 把它们剪掉，同一档 29 分钟跑完，**最优值 1062.4 vs 1062.2 µs
——没丢**。调优脚本值得有一个"按编译代价剪枝"的开关，纯按算法剪枝是不够的。

## 6. 未来方向

按依赖顺序，不是按优先级。

**近期（计算路径）**

1. **低精度权重**（原来排在待评估的第 6 条，o7 之后升到第一）。padding 这条路走死了
   （5.1），单卡路径上剩下的最大一块就是权重流量：这个 shape 权重 2.82 GB，每次 launch
   要整流一遍，o7 量出来单次 stage1 的权重流就是 2.26 ms。int8/fp8 权重直接把 B 流量
   减半，而且它减的是**已经证明按 launch 付、不随行数缩放**的那部分成本——正是 o7 撞上
   的那面墙。仓库里已有 `kernels/gemm/rdna3_int8_gemm.py` 可以起步。精度影响和反量化
   开销还没测，仍属于要先做实验的方向。
2. **把 shape 判据自动化。** 现在 `_SHAPE_TILES` 和 `_SHAPE_M_MAJOR` 是手工表，只覆盖
   测过的 shape。判据本身（权重是否超缓存、A/B 操作数谁更大）是可以算出来的——把它
   写成函数，新 shape 就不用等人来调。这也是让这套优化能推广的关键。
3. **覆盖更多 shape。** 目前只在 `D2048/I768` 和 `D4096/I14336` 上系统调过。
4. **把 `moe_reduce` 折进 gemm2**（o11/o12 之后新出现的）。它做的活只是把 topk 个部分和
   加起来——纯 launch 与往返 DRAM 的开销，M=1 上 4.7 µs、M=760 上 17.8 µs。gemm2
   已经持有那些部分和。挡在前面的是 gfx11 没有 bf16 atomic，所以要么改成 fp32 累加缓冲，
   要么让 gemm2 按 token 而不是按 tile 收尾；两条都要先量一遍，因为**这个 shape 上剩下的
   都是 launch 级的量，很容易被新加的同步吃掉**（o7 就是这么输的）。
5. ~~给原生 vLLM 补调优表~~ —— 做了，见 o13。
6. ~~把 `gate_up` 在 `inter_dim=80` 上的 BLOCK_K 扫完~~ —— 做了，见 o14。内核上现在三个
   尺寸全部领先 tuned triton（−8.8% / −7.9% / −1.2%）。这也把第 4 条降了级：M=1 上
   reduce 只剩 4.7 µs（原来记的 13 µs 是 `_bench_graph` 未修正时的读数），M=760 上
   17.8 µs 而那里已经在 91% 带宽上，折进 gemm2 换不回多少。**M=760 要再拉开只能减权重
   流量**，也就是回到第 1 条的低精度权重。

**中期（EP 路径）**

先看清楚 EP 现在到底缺什么。换 `--shm-size=2g` 的容器之后 EP=4/8 第一次跑通，实测
（`D4096/I14336`，8 专家，同会话，[`BENCHMARK.md` §8](BENCHMARK.md#8-ep-扩展单机多卡到底能走多远)）：

| | EP=1 | EP=2 | EP=4 |
|---|---:|---:|---:|
| prefill 吞吐加速 | 1.00× | 2.05× | **4.15×** |
| decode layer 加速 | 1.00× | 2.00× | **3.76×** |
| 交换占比 prefill / decode | 4.0% / 8.7% | 10.1% / 18.5% | 16.7% / 31.8% |

**扩展性没有问题，所以"多卡"本身不是瓶颈。** prefill 超线性（每 rank 权重变少，layer
从 11.3 ms 降到 9.6 ms）；decode 的 layer 近乎完美线性，因为它是权重带宽绑定的，EP 切
权重就等于切时间。真正会拐弯的地方是交换段：它几乎不随 EP 增长（decode 409 → 478 →
502 µs），但 layer 在缩，外推到 EP=8 时 layer 约 600 µs 而交换约 520 µs——**decode 的
扩展会在 EP=8 附近撞墙，prefill 还早。**

上面这张表和 o1–o10 全部是**弱扩展**：每卡 token 固定，加卡等于加 batch。另一个口径是
固定 batch 再切（`ep_strong_scaling.py`），
问的是"第八张卡还买到了什么"，结论对 prefill 和 decode 相反：

| 固定 batch | EP=2 | EP=4 | EP=8 | 4→8 兑现率 |
|---|---:|---:|---:|---:|
| prefill 8192 token（相对 EP=1） | 2.21× | 4.32× | **7.88×** | 91% |
| decode 256 token（固定容量，相对 EP=1） | 1.76× | 3.40× | **4.65×** | 68% |

**prefill 没到极限，decode 到墙了。** 强扩展下每卡发出的字节按 1/W 缩，所以 prefill 的
交换是**往下走**的（3859 → 2770 → 2245 µs），占比涨到 19% 只是因为它降得比计算慢。
decode 的交换反过来：载荷减半而时间从 416 涨到 480 µs（packed 460 → 579），32 token/卡
早就不在带宽区间，参与者变多只是让每次 collective 更贵。到 EP=8 它吃掉 36.6%，绝对值
在涨，再加卡是负收益。

4. ~~**decode 的固定开销**~~ —— [o9](#o9--固定容量的-dispatch把主机踢出-decode) 做完了。
   固定容量把 counts 交换和回读一起拆掉，EP=4 decode 整层 −10.9%，加图捕获 −11.6%。
   上面外推的"EP=8 撞墙"现在有实测了，而且**墙确实在那儿**：decode 整层 EP=4 → EP=8
   在 packed 下是 1616 → 1463（只快 9%），固定容量下是 1441 → 1305（快 9.4%）。
   layer 本身还在对折，但总时间已经基本不动了。o9 把墙的高度降了约 10%，没有挪走它。
5. **prefill 的交换与计算重叠。** 现在是最大的一块。EP=4 时 1.9 ms 的交换完全串在 9.6 ms
   计算的前后，而传输走 PCIe、计算走 CU，物理上不冲突。按 token 分块流水的上限就是把交换
   全藏掉，约 17%。注意 o9 帮不上这里——固定容量在 prefill 上是 +4.7%，prefill 的交换是
   带宽绑定的，要藏起来而不是缩短。这是架构级改动。
6. **decode 交换里剩下的那块**，现在是单机多卡唯一还剩的 EP 侧目标。o9 之后 EP=4 decode 的交换段还有约 300 µs，其中 payload
   和 meta 两个 collective 各约 50–95 µs 是纯固定开销（EP=1 时 payload 0.00 MB 仍要付）。
   o8 已经否决了把它们合并（+4%，见 5.3），所以这里要么等 5.6 的自研 P2P 路径，要么
   接受它。天花板不大：约 100 µs，decode 整层的 7%。
7. **v4 跨机分层 EP**：两级 group（节点内 L1 复用 v3，节点间 L2），不要一张扁平的
   `nnodes*gpus` all-to-all。combine 的加权仍在 token 老家做。做这个之前先读 5.3 里
   那两个 `all_to_all_single` 的尺寸效应——跨机时块更大、更容易踩。跨机时 o9 的容量
   因子要重新量：节点间带宽更贵，填充的代价也更高。

**明确不做**

- **消除 padding**：o7 量过，整层上限约 11%，而唯一还有希望的做法要改内层循环。见 5.1。
- **合并 dispatch 的 collective**：o8 量过，是 +4%。见 5.3。
- **按 NUMA 挑卡**：GPU0–3 / GPU4–7 分属两个 NUMA 节点，`rocm-smi` 权重 40 vs 72，但
  EP=2 上跨组和组内没有可测差别（跨组甚至略快）。全是 PCIe，瓶颈在根桥不在跳数。
- TP（切专家的 N）：decode 时 all-reduce 太贵，默认 TP=1。
- 把 CDNA 的 mori / `ep_dispatch_intranode` 搬过来：wave64，架构假设不成立。

|---|---:|---:|---:|---:|
| prefill 8192 token 整层加速 | 1.00× | 2.21× | 4.32× | **7.88×** |
| decode 256 token 整层加速（固定容量） | 1.00× | 1.76× | 3.40× | **4.65×** |
| 交换占比 prefill / decode | 2.3% / 4.5% | 9.2% / 12.3% | 12.9% / 23.2% | 19.1% / 36.6% |

prefill 到 EP=8 仍有 1.82×（理想值的 91%），decode 只有 1.37×（68%）且交换绝对值在涨。

EP=4/8 需要 `docker run --shm-size=2g`（RCCL 每 rank 要 20.25 MB，默认 64 MB 只够三个）。

### decode 固定容量（o9）怎么开

```python
# decode：把主机踢出交换段，EP=4 约 −11%，抖动 100 → 3 µs
out = ep_moe_forward(x, w1, w2, ids, weights, tile_m=16, capacity="auto")

# prefill：什么都别传。默认的 packed 才是对的，capacity 在 prefill 是 +4.7%
out = ep_moe_forward(x, w1, w2, ids, weights, tile_m=128)
```

三条必须记住的：

- **全组同一个容量。** 两边都用它切 buffer，而且什么都不交换，所以 rank 之间不一致不会
  报错，只会算错。`"auto"` 按本地 token 数算，token 数不齐的部署要自己传整数。
- **因子取 2**（`capacity_for` 的默认）。取到溢不出来的 `safe_capacity` 反而是 +7.0%。
- **溢出是延迟报的**，最多晚一两步抛 `RuntimeError`，而出事那一步已经带着缺失的行发出去了。
  绝对不能丢行的用 `safe_capacity`，并接受它的带宽。
